=== 2026-07-28 session ===

Engine audited against the BGA implementation (BGA Dump/, now vendored). Domino table,
territory scoring, placement/connection, the 7x7 bound and the discard rule all already
matched. Three fixes:
  - Middle Kingdom: BGA wants the occupied bbox SYMMETRIC about the castle, not merely
    inside a castle-centered 7x7. We were paying +10 on asymmetric boards.
  - Tiebreak: BGA ranks score, then biggestTerritory*100 + totalCrowns. We had no crowns
    level (0.2% of games got the wrong terminal value).
  - Starting claim order: BGA always uses the snake A,B,B,A in 2p ("first player gets first
    and last domino choices"); only which seat is first is random. We modelled the tabletop
    bag draw (6 orders), so 4 of our 6 openings could never occur on BGA.
gen3 earns Middle Kingdom 99.9% of the time under the strict rule, so the lineage lost
nothing to the change. tests/bga_parity.rs transcribes BGA's predicates and asserts parity.

Where the flywheel actually stands:
  - The FPU fix worked. netmcts vs raw gen3 is now MONOTONIC in sims: 16->79.5%, 32->87.8%,
    64->93.8%, 128->94.2%, 256->96.2%, 512->96.5%. The inverted U is gone, so the old "use
    32 sims" lesson is obsolete -- generate at 256-512 now.
  - gen4 still failed though. cap64/cap128 (a capacity A/B on gen3_cap) both lose to gen3:
    best epoch is 1 for both (46.3% / 41.5%), declining monotonically to 28.0% / 13.3% by
    epoch 5. The 5x wider net is WORSE at every epoch despite the best val loss (1.75 vs
    2.02) -- val loss is anti-correlated with strength here, which is why loop.py promotes
    by arena sweep, never by loss.
  - That pattern is overfitting, not a search problem: the teacher is 96% stronger than the
    student's own policy, so the targets are fine; there just isn't enough data.

Root cause of the data starvation, and two bugs behind it:
  1. The JSONL corpus cost 18.4 KiB/record RESIDENT. One 10k-game corpus = 14.1 GiB, and
     loop.py's "train on the last 2 corpora" = 28.2 GiB, which does not fit in 16 GB. That
     is why generations were pinned at 10k games and why loop.py had never actually run
     (no loop_state.json).
  2. --overlap derived a second base seed as `seed ^ PHI`, which collided with the game-seed
     stride (`base + k*PHI`), so pool B replayed pool A's games. Measured: 60 games produced
     31 distinct, 48.3% of records byte-identical duplicates. Every --overlap corpus ever
     generated was ~half duplicates, so "10.3k games" was really ~5.2k.

Fixes: packed binary corpus (kd-features/src/pack.rs, 434 B/record + 4 B/action, memmapped,
Rust batch encoder) and disjoint game-index ranges under one seed. Measured on 201,707
records: load 85.20s -> 0.04s (2290x), python heap 3411 MiB -> 3.1 MiB (1101x), batching
6,781 -> 58,472 rec/s (8.6x). Batches are bit-identical to the old path across all 11
tensors. loop.py --games default raised 10k -> 50k (4M records = ~1.8 GB on disk).

=== 2026-07-29 overnight run (vast.ai 5090 pod) ===

First run of the closed loop that actually completes generations. gen4 -> gen10, six
promotions unattended, then 5 consecutive failures at gen11 ended it.

Throughput on a 5090 (32 cores, 92 GB): 31.1 games/s single process at 256 sims, 33% GPU.
Batch size is NOT the lever -- throughput is flat across concurrent=1024..8192 (30.9, 30.3,
28.1, 28.2 games/s). Sharding is: 2 procs = 41.7 games/s at 66% GPU, 3 = 42.9 at 74%. The
knee is 2. The GPU is launch-bound, not data-starved: a 133k-param net on 13x13 boards
issues too many tiny kernels, so filling the timeline does not convert into throughput.
Real fixes would be CUDA graphs or MPS; not worth it yet.

WATCH OUT: nvidia-smi samplers that outlive the run poison the average. A 3-proc run showed
"32% GPU" over 2125 samples for a 287s run -- the true active-window figure was 74%.

The important result is that the promotion CHAIN is not a ranking. Common-opponent ladder,
1200 games each vs gen4 (+/-2.8):
    gen5 55.0 | gen6 59.5 | gen7 57.3 | gen8 57.0 | gen9 58.3 | gen10 60.3
gen7 and gen8 are worse than gen6. Those were the coin-flip promotions the point-estimate
gate allowed (50.3%, 50.1% vs their immediate predecessor). Head-to-head, gen10 vs gen6 is

  - real progress: gen4 -> gen6 (+9.5 pts vs gen4)
  - gen7..gen10: ~3.5 h of GPU time, no measurable gain
  - the plateau began at gen6, four generations before the loop noticed at gen11

--promote-rule point does not merely risk drift, it spent four generations on it. Next run:

Untested levers for the plateau, in rough order of expected value: (1) wider replay window

=== 2026-07-29 afternoon: four experiments against the gen11 plateau ===

Setup for all of these: train on gen-N-generated corpora, evaluate against that same champion,
so only the named variable moves. Numbers are win% with 95% CI.

1. WINDOW x CAPACITY, 2x2 factorial on gen10 data (vs gen10, +/-2.8):
                 ch=64                        ch=128
   window 2   51.7  peak ep1 -> 46.7      52.9  peak ep1 -> 40.8
   window 4   53.0  rises to ep3, holds   55.1  rises to ep3, ep2-5 all significant
   An INTERACTION, not two effects: capacity alone is worse than useless (ch=128 on a
   2-generation window collapses harder than ch=64 on the same data), data alone barely clears
   the control, both together is the best arm measured AND the most stable. Also settles why
   cap128 failed back at 10k games: starvation, not capacity. w4_ch128.epoch3 was promoted as
   gen11 (55.1% vs gen10, LCB 52.3).

2. EPOCH COUNT -- 12 epochs, sparse sweep at 2000 games/point (+/-2.2), vs gen11:
     ep1 48.8 | ep3 44.9 | ep5 52.0 | ep7 46.6 | ep9 39.5 | ep12 44.5
   Peaks at 5, monotonic collapse after (-5.4 then -7.1, both outside the CIs). --epochs 5 is
   about right. The "epoch 5 best and still climbing" seen in single loop attempts was the top
   of a curve, not a truncated rise. NOTE: train.py has NO LR schedule (constant Adam 1e-3), so
   a 12-epoch run is directly comparable to a 5-epoch one -- no schedule confound.

3. 512 SIMS -- FAILED, and it cost 2x per generation. Phase A showed 512-sim search beats
   256-sim search head-to-head at gen10 (53.2%, significant), which justified trying it. But
   playing better does NOT mean teaching better: the loop ran attempts 14-18 at 512 sims,
   window 4, ch 128, and every one failed. Attempt 18's window was fully 512-sim (no legacy
   256-sim data) and scored 48.9%. Pooled over the 5 attempts: 50.3% +/- 1.4 over 5000 games,
   i.e. exactly gen11. Do not retry 512-sim generation without a different reason.
   METHOD NOTE: comparing two strong agents against a WEAK common opponent compresses their
   difference (256 and 512 sims both scored ~96% vs a raw net and looked identical). Rank strong
   agents head-to-head. The mirror-image trap is comparing two nets WITH search on both sides,
   which masks policy differences -- use raw-vs-raw for that.

4. WHERE THE PLATEAU ACTUALLY IS -- the important result:
     netmcts:512:gen11 vs RAW gen11   97.2% +/- 0.7
     netmcts:128:gen11 vs RAW gen11   94.3% +/- 1.0
     RAW a17.ep5      vs RAW gen11    51.0% +/- 1.5  (4000 games)
     RAW a16.ep4      vs RAW gen11    50.3% +/- 1.5  (4000 games)
   The targets contain a 97% improvement over the policy that generated them, and training
   extracts NONE of it -- confirmed raw-vs-raw, so it is not the arena masking it. This is the
   AlphaZero fixed point: the net has converged to the best policy its architecture can express,
   so better targets return the same net. A 97% search-vs-raw gap is very wide (mature setups
   run 70-80%), which points at too little capacity to represent the search.
   Next test: ch=256 on the same window, matched against attempt 18's ch=128 (same window, same
   seed 18) -- if capacity is the ceiling, ch=256 clears 50% raw-vs-raw.

TOOLING NOTE: raw-vs-raw arena runs at ~2400 games/s vs ~15 with 512-sim search. 4000 games
costs seconds and gives +/-1.5, so policy-quality questions should be asked raw, not through
search.
